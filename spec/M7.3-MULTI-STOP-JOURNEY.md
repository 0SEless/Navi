# M7.3 — Multi-Stop Journey

## Problem

M7.1 proved point-to-point workflows. M7.2 proved the same workflow can produce different
behavior via policy. Both validate the single-destination case.

M7.3 asks a fundamentally different question:

> **Can Journey represent workflows that don't terminate after one destination?**

If no, the model is point-to-point specific — a limitation that will surface as soon as
someone wants a campus tour, delivery route, admissions checklist, or maintenance
inspection walkway.

If yes, Journey is genuinely generic: it models transitions, not destinations.

## Architectural Hypothesis

> **A Journey is defined by transitions, not by destinations. Multi-stop is not a new
> workflow — it's the same workflow applied repeatedly.**

The corollary: removing all but one stop from a multi-stop journey should produce the
same workflow as a single-destination `VisitorJourneyService`. M7.1 is a degenerate case
of M7.3.

## Principle

> **No new step types.**

Prove that the existing 8 `JourneyStep` variants (`locate`, `search`, `navigate`,
`arrive`, `panorama`, `select-destination`, `select-entrance`, `confirm`) are sufficient
for multi-stop workflows.

If a new step type is required, the Journey model is incomplete and must change. But the
hypothesis is that the existing vocabulary is general enough — the only difference is the
sequence.

## Workflow

Multi-stop uses the same vocabulary, repeated:

```
begin({ origin, stops: ["Stop A", "Stop B", "Stop C"] })
    ↓
LocateStep
    ↓
NavigateStep → Stop A
    ↓
ArrivalStep (Stop A)
    ↓
PanoramaStep (optional)
    ↓
NavigateStep → Stop B
    ↓
ArrivalStep (Stop B)
    ↓
PanoramaStep (optional)
    ↓
NavigateStep → Stop C
    ↓
ArrivalStep (Stop C)
    ↓
PanoramaStep (optional)
    ↓
Complete
```

Every transition is an existing step type. The workflow never branches into tour-specific
states.

## What M7.3 Must Prove

### 1. JourneyContext can express "more destinations remain"

Right now `JourneyContext` has:

```ts
resolvedDestinationId?: string
```

M7.3 adds a general mechanism for sequencing — these are ordered work items, not
tour concepts. The same fields would serve delivery routes, maintenance checklists,
or admissions itineraries:

```ts
currentStop?: string           // the stop currently being worked on
remainingStops: string[]       // requested stops not yet reached
completedStops: string[]       // stops the user has reached
```

Execution state is always three sets: **completed → current → remaining**. Rather than
inferring the active stop as `remainingStops[0]`, the context explicitly tracks it.
This makes rerouting, skipping, or inserting stops a mutation of the stop queue rather
than a change to Journey itself.

`remainingStops` holds the original request text, not search result IDs, because
search resolution happens inside `advance()`.

### 2. The same `advance()` transition table works (including interaction)

| Current Step | Condition | `advance()` produces |
|---|---|---|
| `locate` | single result | Resolve first stop → `Navigate` |
| `locate` | multiple results | `SelectDestination` (waiting-on-user) |
| `select-destination` | responded | `Navigate` |
| `arrive` | more stops remain | Resolve next stop → `Navigate` |
| `arrive` | no stops remain | `Complete` (or `Panorama` if available) |

The only new logic: after `arrive`, check if `remainingStops` is non-empty. If yes,
derive the next NavigateStep. If no, terminate. The interaction path (select-destination)
is unchanged from M7.1b — it works identically for any stop whose search returns
multiple results.

### 3. A single stop is indistinguishable from a Visitor Journey

```ts
const multi = service.begin({ origin, stops: ["Library"] })
const single = visitorService.begin({ origin, stops: ["Library"] })

// Both journeys produce identical steps and structure
expect(multi.steps.map(s => s.kind)).toEqual(single.steps.map(s => s.kind))
expect(multi.steps[1].route).toEqual(single.steps[1].route)
```

That is the strongest regression test — it proves the single-destination workflow didn't
need its own service all along.

## API Evolution

### JourneyRequest — single internal representation

Inside the runtime, `JourneyRequest` always uses an ordered list of stops:

```ts
interface JourneyRequest {
  origin: LatLng
  stops: readonly string[]
  routing?: RoutePreferences
}
```

This keeps the rest of the service branch-free — it always iterates `stops`.

Convenience overloads on `begin()` normalize single-destination calls:

```ts
begin(origin: LatLng, destination: string): Journey           // wraps to { stops: [destination] }
begin(request: JourneyRequest): Journey                        // explicit stops
```

Internally, both normalize to a single representation. There is exactly one code path.

### No new service

`VisitorJourneyService` already handles the workflow. M7.3 extends it — the same class
counters `stops.length` and adjusts the transition logic accordingly.

This keeps the proof tight: the same composition service, the same step types, the same
engine — just a richer request.

## Acceptance Criteria

1. **No new JourneyStep variants.** The existing 8 types are sufficient.
2. **No new composition service.** `VisitorJourneyService` handles both single and multi.
3. **`JourneyRequest.stops` is `readonly string[]`.** Single-stop convenience overloads
   normalize to this internally — one representation, one code path.
4. **Multi-stop workflow produces the correct sequence.** For N stops, the journey
   produces: `locate`, then N × (`navigate`, `arrive`, optional `panorama`), then
   `complete`.
5. **Single-element array is identical to `begin(origin, "Library")` overload.** Same
   steps, same routes, same behavior.
6. **Empty stops array marks journey as failed immediately.** The service rejects
   at `begin()` rather than failing mid-workflow.
7. **Interaction steps work mid-sequence.** If any stop's search returns multiple results,
   `select-destination` pauses the workflow (same as M7.1b).
8. **`JourneyContext` uses sequencing fields, not tour-specific fields.**
   `currentStop`, `remainingStops`, `completedStops` — not `tourStops`,
   `tourOrder`, `campusTourMode`. Execution state is always three sets:
   completed → current → remaining.
9. **Removing all but one stop from a multi-stop request produces a Visitor Journey.**
   The architectural regression test.
10. **Layer-boundary gate passes.** Same 5+ composition files, zero forbidden imports.
11. **Full workspace suite remains at 1056+ tests with zero failures.**

## Explicitly Out of Scope

- Tour narrative or commentary (audio guide, text descriptions)
- Tour ordering optimization (nearest-first, building-to-building)
- Tour scheduling (time-based, opening hours)
- Tour sharing or publishing
- Dynamic reordering mid-journey
- Tour themes or categories
- Any UI for tour creation or editing
- Scenic vs direct routing between stops
- Estimated completion time for multi-stop journeys

## Technical Considerations

- `JourneyRequest.stops: readonly string[]` is the single internal representation.
  Convenience overloads normalize `begin(origin, "Library")` to `{ stops: ["Library"] }`.
  There is no branching on `typeof destination` inside the runtime.
- `remainingStops` is populated at `begin()` from the stops array. These are the original
  request strings, not search result IDs — search resolution happens inside `advance()`.
  The service shifts from `remainingStops` to `completedStops` as each stop is reached.
- `advance()` checks `remainingStops.length > 0` after arrival to decide whether to
  navigate to the next stop or complete. This is a single if-else branch — the
  multi-stop path shares all existing navigation-building logic.
- The backtracking check (previous stops remain reachable) is not required for M7.3.
  The service assumes the user is progressing forward.

## Known Pitfalls

- **Creating step types for multi-stop concepts.** The existing vocabulary is sufficient.
  Resist `WaypointStep`, `TourStopStep`, `NextStopStep`.
- **Hardcoding "tour" language into JourneyContext.** Use sequencing fields
  (`currentStop`, `remainingStops`, `completedStops`), not tour fields. These represent
  ordered work items — they also model delivery routes, maintenance checklists, and
  security patrols.
- **Adding tour-specific validation.** Multi-stop is about sequencing, not sightseeing.
  Don't validate that stops are in a sensible order or that they form a coherent tour.
- **Maintaining two internal representations.** The `begin(origin, destination)` overload
  must normalize to `{ stops: [destination] }` internally. Never branch on
  `typeof destination` inside `advance()`.
