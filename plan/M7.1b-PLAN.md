# M7.1b — VisitorJourneyService Plan

Based on `spec/M7.1b-VISITOR-JOURNEY-SERVICE.md`. Implements the first real composition
service that proves the M6 capability vocabulary is sufficient for point-to-point workflows.

## Architecture Invariants (from spec)

- Capability dependency only: no graph, package, artifact, compiler, loader, or viewer types
- `advance()` derives exactly one transition per call — never batch-generates
- A composition service may append new steps but shall never mutate completed steps
- `failed` status = unrecoverable capability error only
- Search internalization: single-result search does not produce a SearchStep
- Panorama optionality: PanoramaStep only if panorama available

## Tasks

### T1 — VisitorJourneyService

**Files to touch:**
- `packages/runtime/src/composition/visitor-journey-service.ts` (create)

**What:**
A class that implements `CompositionService` and proves the architecture:

```ts
class VisitorJourneyService implements CompositionService {
  constructor(private readonly engine: RuntimeEngine)

  begin(position: LatLng, destination: string): Journey {
    // 1. engine.location.resolve(position) → LocateStep
    // 2. engine.search.search(destination)
    //    - Single result: set context.resolvedDestinationId = result.id
    //    - Multiple results: create SelectDestinationStep with candidates
    // 3. Return Journey — no cache, no hidden state
    //    Context stores only continuation data, never capability results
  }

  advance(journey: Journey): Journey {
    // Transition table determines what to produce from current state.
    // Reads context for continuation data (resolvedDestinationId).
    // Reads step data for candidates (SelectDestinationStep.candidates).
    // Calls only the capabilities needed for this transition.
  }
}
```

**Key decisions:**
- `begin()` establishes initial execution state only — it never calls `buildings` or
  `navigation`. Those are derived lazily by `advance()`. This keeps the API behavior
  consistent regardless of whether search yields one result or many.
- **No internal cache.** The service stores zero state between calls. All continuation
  data lives in `Journey.context` — a lightweight execution state object.
- `Journey.context` stores only continuation context (`resolvedDestinationId`), never
  duplicated capability results (no SearchResult[], BuildingResult, Route, Panorama).
- `advance()` reads context + current step data + calls capabilities → appends step.
  It never re-searches.

- `advance()` uses a deterministic transition table:

| Current Step | Context | `advance()` produces |
|---|---|---|
| `locate` | `resolvedDestinationId` set | `buildings.resolve` + `navigation.findRoute` → `Navigate` |
| `locate` | candidates stored (multi-result) | `SelectDestination` (waiting-on-user) |
| `select-destination` | `resolvedDestinationId` set (via respond) | `buildings.resolve` + `navigation.findRoute` → `Navigate` |
| `navigate` | — | `Arrival` |
| `arrive` | — | `Panorama` (optional) or `Complete` |
| `panorama` | — | `Complete` |
| `complete` | — | No-op |

- `advance()` is idempotent — if called when no transition is possible, it returns
  the journey unchanged.
- The service never stores state between calls; all state lives in the Journey instance.

**Edge cases handled by begin():**
- `location.resolve()` throws → journey status = `failed`
- `search.search()` returns empty results → journey status = `failed` (no destination possible)
- `search.search()` returns one result → internal, no SearchStep; stores resolved destination
- `search.search()` returns multiple → SelectDestinationStep, status = `waiting-on-user`

**Edge cases handled by advance():**
- `buildings.resolve()` returns undefined → journey status = `failed`
- `navigation.findRoute()` returns undefined → journey status = `failed`
- `panoramas.resolve()` and `panoramas.findNearest()` both return undefined → no PanoramaStep
- Called when no more transitions possible → returns unchanged (idempotent)
