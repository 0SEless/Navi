# M7.2 — Routing Preferences

## Problem

M7.1b proved a complete visitor workflow can be derived using only the five M6 capabilities.
It validated the composition vocabulary. But it used only one navigation implementation.

M7.2 asks a harder question:

> **Can the same workflow produce different behavior solely by changing a preference?**

If yes, then the separation between **domain knowledge (M6)** and **workflow (M7)** is proven
at the architectural level — composition services express intent, capabilities determine behavior.

## Architectural Hypothesis

> **Composition services should express *intent*, while capabilities determine *behavior*.
> M7.2 validates this by changing only routing preferences while leaving workflow structure
> unchanged.**

A corollary: `VisitorJourneyService` shall compile and behave correctly regardless of whether
the caller requests standard or accessible routing, because routing policy is wholly determined
by the Navigation capability.

## Principle

> **Separate composition services exist when the *workflow* changes. A preference is not a
> workflow.**

Accessibility does not deserve its own service. It deserves a parameter.

| Change level | Example | Mechanism |
|---|---|---|
| Routing preference | Accessible vs standard | `RoutePreferences` |
| Workflow structure | Tour vs point-to-point | New composition service |

## Minimal API Evolution

### JourneyRequest

The `begin()` signature grows to carry preferences without proliferating positional parameters:

```ts
interface JourneyRequest {
  origin: LatLng
  destination: string
  routing?: RoutePreferences
}
```

```ts
begin(request: JourneyRequest): Journey
```

### RoutePreferences

```ts
interface RoutePreferences {
  mode?: RouteMode
}

type RouteMode = 'standard' | 'accessible'
```

`RouteMode` is closed to exactly two values because only two exist today.
The `mode` parameter is optional and defaults to `'standard'`.

### NavigationService

```ts
findRoute(fromId: string, toId: string, preferences?: RoutePreferences): Route | null
```

Optional parameter preserves backward compatibility with all existing callers.

## Workflow

Unchanged from M7.1b.

```
begin({ origin, destination })
    ↓
LocateStep
    ↓
advance()
    ↓
NavigateStep (routing respected)
    ↓
advance()
    ↓
ArrivalStep
    ↓
advance()
    ↓
PanoramaStep (optional)
    ↓
advance() → complete
```

The only difference: `advance()` calls `engine.navigation.findRoute(from, to, request.routing)`
instead of `engine.navigation.findRoute(from, to)`.

## What Changes

| Component | Change |
|---|---|
| `VisitorJourneyService.begin()` | Accepts `JourneyRequest` instead of positional params |
| `@navi/core` types | New `RouteMode`, `RoutePreferences` |
| `packages/runtime/src/composition/` | New `JourneyRequest` type (workflow input, not domain contract) |
| Navigation capability | `findRoute` accepts optional `RoutePreferences` |
| Everything else | Unchanged |

## What Does NOT Change

- `Journey` model
- `JourneyStep` variants (no new step types)
- `JourneyContext`
- `LocationService`, `SearchService`, `BuildingService`, `PanoramaService`
- `RuntimeEngine` type
- Layer-boundary gate
- Existing M7.1b tests
- Existing M7.0 contract test

## Acceptance Criteria

1. **`VisitorJourneyService` is the only point-to-point composition service.** Future
   workflow types (CampusTour, Emergency, Delivery) will be separate services.

2. **Workflow unchanged.** Same `Journey` model, same `JourneyStep` variants, same
   interaction protocol — regardless of the `mode` preference.

3. **No new step types.** Accessibility is a routing policy, not a workflow.

4. **No graph inspection.** The service never accesses graph, package, artifact,
   compiler, loader, or viewer types.

5. **The only observable difference between `mode: 'standard'` and `mode: 'accessible'`
   is the produced `NavigateStep.route`.** All other steps (Locate, Search, Select,
   Arrival, Panorama) are identical for the same input.

6. **Regression test.** Given identical `JourneyRequest` except for `routing.mode`,
   the two journeys produce different `Route` values in `NavigateStep` but identical
   everything else.

7. **Backward compatibility.** `VisitorJourneyService.begin(origin, destination)` still
   compiles (old callers are not forced to migrate immediately — both overloads or a
   migration period. Ideally the old signature delegates to the new one internally.)

8. **Layer-boundary gate passes.** Zero forbidden imports across all composition files.

9. **Existing M7.1b tests continue to pass.** Full workspace suite remains at 1056+
   tests with zero failures.

## Explicitly Out of Scope

- Multi-preference selection mid-journey
- Preference negotiation
- Route comparison UI
- Any new interaction step types for accessibility
- Building-level accessibility data
- Real accessibility graph data
- Multi-stop or tour workflows
- A second composition service

## Technical Considerations

- `JourneyRequest` replaces positional `(position, destination)` in the `begin()` signature.
  A transitional overload can preserve the old signature for a migration window.
- Default parameter on `findRoute` preserves backward compatibility — existing callers
  (M7.0 contract test, M7.1b tests) continue to work without changes.
- The layer-boundary gate (`scripts/check-layer-boundaries.mjs`) continues to check the
  same files (5 composition files).
- `AccessibleNavigationService` (a concrete variant that prefers accessible routes) is in
  scope only as a test fake, proving the routing path differs.

## Known Pitfalls

- **Over-investing in `RoutePreferences` before the second mode exists.** Only define
  `mode?: 'standard' | 'accessible'`. Do not add `indoor`, `scenic`, `fastest` etc.
- **Temptation to add accessibility branches inside the composition service.**
  If you find `if (stairs)`, `if (wheelchair)`, `if (elevator)` in the service,
  those decisions belong inside the navigation capability.
- **Making accessibility a JourneyStep kind.** Accessibility is a routing preference,
  not a workflow state.
- **`JourneyRequest` scope creep.** Only define fields needed now (`origin`,
  `destination`, `routing`). Resist adding `language`, `timeConstraints`,
  `visitorRole`, `tourPreferences` — those belong in later milestones.
