# M7.1b — VisitorJourneyService

## Problem

M7.1a defined the workflow vocabulary (`Journey`, `JourneyStep`, interaction protocol).
M7.1b must prove that vocabulary is sufficient for a real point-to-point journey using
only the five M6 capabilities.

If M7.1b succeeds without changing any M6 API, the M6 vocabulary is validated as complete
for all foreseeable composition workflows.

## Principle

> **VisitorJourneyService derives workflow only. Every domain fact must originate from an M6
> capability.**

## Workflow (Visitor Journey)

The following is the current step sequence for VisitorJourneyService. Journey itself does
not prescribe any fixed sequence — different composition services may emit different step
sequences while using the same Journey model.

```
begin(position, "Library")
    ↓
LocateStep
    ↓
advance()  ──→  SearchStep [internal if 1 result]
    ↓
SelectDestinationStep          if multiple → waiting-on-user
    ↓
respond(id)  ──→  advance()
    ↓
NavigateStep
    ↓
advance()
    ↓
ArrivalStep
    ↓
advance()
    ↓
PanoramaStep [optional]        only if panorama available
    ↓
advance()  ──→  complete
```

## How Derivation Works

**`begin()` produces only the steps determinable from the initial query.**
It creates a Journey starting with `LocateStep`, then `SearchStep`, then either
`NavigateStep` (if search returns exactly one result) or `SelectDestinationStep`
(if multiple). It cannot know the route or panorama before the user has chosen.

**`advance()` derives exactly one transition.** It inspects the current journey state,
calls the necessary capabilities, appends the next determinable step, and returns the
same Journey instance. It does not batch-generate remaining steps.

This incremental approach keeps the Journey as **evolving execution state**, not a
pre-populated script. It also makes later composition services tractable — rerouting,
accessibility alternatives, and multi-stop tours all benefit from single-step derivation
because the service can re-evaluate after each user action or sensor event.

## Invariants

1. **A Journey may derive future workflow from previous results, but must never duplicate
   capability knowledge.** Step data references capability results; it does not copy them
   into a parallel data model.
2. **Search should not always produce a SearchStep.** If the search returns exactly one
   result, the search is internal to the service and the workflow proceeds from LocateStep
   directly to NavigateStep.
3. **Panorama is optional after arrival.** A PanoramaStep is only produced if a panorama
   is available for the destination. This avoids assuming every building has one.
4. **JourneyStep is immutable.** Steps are readonly snapshot DTOs representing completed
   work, not pending actions.
5. **A composition service may append new steps but shall never mutate or replace
   previously completed steps.** This gives the Journey event-sourcing-like semantics:
   history stays intact for rerouting, accessibility, analytics, debugging, and replay.
6. **Journey owns navigation.** `next()`, `previous()`, `respond()`, `reset()` are on
   Journey. The service owns derivation; Journey owns progression.

## Capability Dependencies

> **VisitorJourneyService depends only on the public contracts of the five runtime
> capabilities.** The current implementation uses these methods:

```
engine.location.resolve(position)
engine.search.search(query)
engine.buildings.resolve(buildingId)
engine.navigation.findRoute(from, to)
engine.panoramas.resolve(nodeId)
engine.panoramas.findNearest(position)
```

No graph, package, artifact, compiler, loader, or viewer APIs.
No direct access to `LoadedPackage` or any M1–M5 type.

## Public API

```ts
class VisitorJourneyService implements CompositionService {
  constructor(engine: RuntimeEngine)

  begin(position: LatLng, destination: string): Journey
  advance(journey: Journey): Journey
}
```

- `begin()` creates a Journey with the steps that can be derived without user input.
- `advance()` takes a Journey that has just been responded to (or needs its next step
  derived), derives the **next determinable step** from the current state, appends it,
  and returns the same Journey instance.

The application drives execution like this:

```ts
let journey = service.begin(position, "Library")

while (!journey.isComplete()) {
  const step = journey.current()

  if (journey.status === 'waiting-on-user') {
    const input = await renderInteraction(step)
    journey.respond(input)
    journey = service.advance(journey)
  } else if (/* end of known steps */) {
    journey = service.advance(journey)
  } else {
    render(step)
    journey.next()
  }
}
```

The service does NOT expose `next()`, `previous()`, or `respond()` — those belong to
`Journey`.

## Explicitly Out of Scope

These are valid composition concerns for later milestones, not M7.1b:

- Accessibility-aware routing
- Building closures / operating hours
- Visitor permissions / role-based journeys
- Emergency rerouting
- Event-aware destination selection
- Guided campus tours (multi-stop)
- ETA optimization
- Alternative route selection
- Panorama as mandatory step (it is optional)

## Acceptance Criteria

1. `begin(position, "Library")` returns a `Journey` with at least `locate`, `search`,
   and either `navigate` (single result) or `select-destination` (multiple results).
2. When search returns exactly one result, the journey proceeds directly from `locate`
   to `navigate` — no `SearchStep` or `SelectDestinationStep` is exposed.
3. When search returns multiple results, the journey pauses on `select-destination`
   (`status: 'waiting-on-user'`) until `respond(candidateId)` is called.
4. `advance()` derives exactly one transition per call. Multiple calls produce
   `navigate`, `arrive`, and optionally `panorama` steps sequentially.
5. The journey completes after the final step (`status: 'complete'`).
6. If no panorama is available for the destination, `PanoramaStep` is omitted and the
   journey completes after `ArrivalStep`.
7. Replacing any M6 capability implementation (e.g., `NavigationService` →
   `AccessibleNavigationService`) without changing `VisitorJourneyService` is possible
   because the service depends only on the capability contract.
8. The service passes the layer-boundary gate: zero forbidden imports.
9. The full workspace test suite remains at 1056+ tests with zero failures.

## Technical Considerations

- **File:** `packages/runtime/src/composition/visitor-journey-service.ts`
- **Tests:** `packages/runtime/src/composition/__tests__/visitor-journey-service.test.ts`
- **Dependencies:** `RuntimeEngine`, `Journey`, `JourneyStep` types, M6 capability DTOs
- **Stateless service:** All workflow state lives in the `Journey` instance. The service
  is stateless between calls.
- **Error propagation:** `failed` status indicates the workflow cannot continue because
  an unrecoverable capability error occurred (e.g., `location.resolve()` throws). It does
  not cover recoverable situations like "destination closed" or "no panorama available" —
  those are handled as interaction steps or optional step omission.
- **Search internalization:** The service internally calls `search.search()`. If the
  result is a single match, no `SearchStep` is added to the Journey — the search is
  treated as a deterministic resolution, not a user-facing step.
- **Panorama optionality:** `advance()` checks `panoramas.resolve(nodeId)` and
  `panoramas.findNearest(position)`. Only if at least one returns a result is a
  `PanoramaStep` appended.
