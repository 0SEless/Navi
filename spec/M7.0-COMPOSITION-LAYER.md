# M7.0 — Composition Layer (Architectural Milestone)

## What

M7 is a **different category** of work from M1–M6. M1–M6 each introduced exactly one *layer*
(data pipeline → runtime vocabulary). M7 introduces **composition services**: components that
own *workflow*, not *data*, and orchestrate the frozen M6 capabilities (ADR-015) to fulfil
user journeys.

This milestone (M7.0) is **architectural first**. It defines the composition model — the rules
every M7 service obeys — **before** any concrete service (`VisitorJourneyService`,
`AccessibilityNavigationService`, `CampusTourService`) is implemented. M7.1+ are only permitted
once this model is accepted.

The full stack now reads:

```
Studio
    │
Compiler
    │
Publisher
    │
Package
    │
Loader
    │
Runtime Capabilities   (M6 — frozen baseline, ADR-015)
    │
Composition Services   (M7 — this layer)
    │
Applications
```

### Invariants (carried from ADR-013/014/015)

- **M6 is the floor.** Composition services are built **only** on the five capability
  properties of `RuntimeEngine` (`navigation`, `search`, `buildings`, `location`,
  `panoramas`). They never read artifacts directly, never bypass the façade.
- **Composition owns workflow, not data.** A composition service adds sequencing,
  state-machine flow, and cross-capability coordination. It does not expose new low-level
  runtime primitives.
- **Composition services derive workflows, never new facts.** Capabilities answer questions;
  composition arranges answers. A composition service combines capability results into a user
  workflow (e.g. "Take me to Library") without introducing any new data the capabilities could
  not already supply. No new knowledge enters the system at the composition layer.
- **Composition owns intent, not execution.** A composition service describes *what should
  happen next*; it never performs the action. It may emit a workflow of intent steps
  (`{ type: 'navigate', destination: 'Library' }`, `{ type: 'viewPanorama', panoramaId: 'p1' }`,
  `{ type: 'search', query: 'Computer Lab' }`) but must never call `viewer.loadPanorama(...)`,
  `map.flyTo(...)`, `navigator.geolocation.watchPosition(...)`, or any other platform/UI API.
  Execution belongs to the application layer. This keeps composition completely
  platform-independent — the same service works behind a React web app, a mobile app, or a
  desktop app. (This is the composition-layer analogue of M6's viewer-agnostic rule.)
- **Dependency graph is explicit and one-way.** A composition service depends only on:
  `RuntimeEngine`, domain DTOs, and other composition services. It must **never** depend on
  `LoadedPackage`, artifact types, or any pipeline module.
  ```
  Application
        │
  Composition Service
        │
  RuntimeEngine
        │
  Capabilities
        │
  Artifacts
  ```
  Forbidden (machine-verified by the layer-boundary gate):
  ```
  Composition → LoadedPackage   ❌
  Composition → SearchIndex     ❌
  Composition → Graph           ❌
  Composition → compiler/*      ❌
  Composition → publisher/*     ❌
  Composition → loader/*        ❌
  ```
  **Allowed imports:** `RuntimeEngine`, domain DTOs (`@navi/core`), other composition services.
  **Forbidden imports:** `compiler/*`, `publisher/*`, `loader/*`, `graph/*`, artifact/index
  types (`LoadedPackage`, `NavigationGraph`, `SearchIndex`, `BuildingIndex`, `PanoramaIndex`, …).
- **No new artifact pipeline.** M7 does not extend the compiler/publisher/loader with new
  artifacts. If a feature needs data M6 doesn't publish, that is an M6 (capability) change
  gated by ADR-015 — not a silent composition-side workaround.

## The Composition Model — answered questions

### 1. What makes something a composition service?

A composition service satisfies **all** of:

- Constructed from `RuntimeEngine` only — never from `LoadedPackage` or raw artifact data
  (see the explicit dependency graph above).
- Its public methods return **journey/workflow results** (e.g. a sequenced itinerary, a
  reachable accessible route, a tour script), not raw capability DTOs re-exposed.
- Every data question it answers is delegated to a capability. It holds no copy of graph,
  index, or panorama state.
- It is named for the *user journey* it serves (`VisitorJourney`, `AccessibilityNavigation`,
  `CampusTour`), not for a data domain.

If a proposed service would read an artifact directly or add a new artifact-backed primitive,
it is misclassified and must become an M6-style capability (its own ADR + artifact pipeline).

### 2. Can composition services depend on each other?

**Yes, but acyclically.** Composition services may depend on other composition services,
provided the dependency graph is acyclic (no service composites another that composites it).
Dependencies are expressed by constructor injection of the depended-on service (or of
`RuntimeEngine`, from which the dependency is read). A lower-level composition service
(e.g. `CampusTourService`) may use a higher-level one only if that does not create a cycle;
prefer composing toward the application, not among peers.

### 3. Can they hold state?

**Limited, explicit, journey-scoped state only.** A composition service may hold state that
represents an *in-progress workflow* (e.g. the current step of a visitor journey, a tour
playback position). This state:

- Is **not** persistent across `RuntimeEngine` lifetimes unless the application explicitly
  persists it.
- Is **not** a cache of capability data — re-query the capability on each transition.
- Must be safe to discard: constructing a fresh service on the same engine yields a fresh,
  idle workflow.

Statelessness of the *underlying capabilities* (ADR-013) is untouched; composition state is a
separate, explicitly-scoped concern.

### 4. Are they synchronous?

**Method calls are synchronous and non-blocking by default.** A composition service composes
capability calls (which are synchronous, deterministic) and returns a result. It must **not**
perform I/O, network, or async viewer work internally. If a journey needs async steps (e.g.
awaiting user input between tour stops), the *application* drives those transitions; the
service exposes explicit step methods (`next()`, `current()`) and remains synchronous.

### 5. Do they expose workflows or data?

**Workflows.** A composition service exposes operations that advance or describe a *journey*
(an itinerary, a step sequence, a route with context). It may return *derived* view models
that bundle several capability results into a journey shape, but it does not re-expose raw
capability DTOs as if it were a capability. The application renders from the journey model.

**Composition services derive workflows, never new facts.** Capabilities answer questions;
composition arranges answers. No new data enters the system at this layer. Example:

```
Search        → "What is Library?"        → Library entry
Building      → "Where is Library?"       → building + floor
Navigation    → "How do I get there?"     → route
Panorama      → "What will I see?"        → panorama at destination
```

A composition service combines those answers into a single workflow:

```
"Take me to Library."   →  { destination, route, arrivalPanorama }
```

Notice what happened: **no new knowledge appeared — only orchestration.** That is the essence
of composition, and it is the test every M7 service must pass: if a feature needs a fact no
capability can supply, that fact belongs in the pipeline (M6 capability), not in composition.

### 5b. Intent vs execution (the platform-independence test)

Composition owns **intent**, not **execution**. A composition service may *describe* what
should happen next; it must never *perform* it.

Allowed — a composition service emits intent steps:

```ts
// VisitorJourneyService.plan("Library") returns a workflow of intent:
[
  { type: 'navigate', destination: 'Library' },
  { type: 'viewPanorama', panoramaId: 'p1' },
  { type: 'search', query: 'Computer Lab' },
]
```

Forbidden — a composition service must never call platform/UI APIs:

```ts
viewer.loadPanorama(...)        // ❌ application layer
map.flyTo(...)                  // ❌ application layer
navigator.geolocation.watchPosition(...)  // ❌ application layer
```

The rule in one line:

> A composition service says **what should happen next** — never **how the UI performs it.**

This is what makes composition completely platform-independent: the same `VisitorJourneyService`
works unchanged behind a React web app, a mobile app, or a desktop app. It is the exact
analogue of M6's viewer-agnostic rule, lifted one layer up.

### 6. How are they tested?

- **Unit:** construct with a real or faked `RuntimeEngine` (the frozen five capabilities),
  assert journey outputs and step transitions. Fakes implement the capability *interfaces*
  (stable per ADR-015), so tests are immune to capability implementation churn.
- **Integration:** drive a real `RuntimeEngine` over a loaded test package; assert end-to-end
  journey correctness (e.g. a visitor journey resolves a destination, finds a route, attaches
  a nearby panorama).
- **Invariant tests:** assert the service never reads artifacts directly (grep/import gate) and
  that its method signatures are stable.

## Success Criteria (for M7.0 acceptance)

1. The composition model above is accepted and recorded (this SPEC + the M7.0 PLAN).
2. A capability-interface boundary is explicit so composition services can be faked in tests
   without loading a package.
3. At least one *reference* composition service exists as the template (its shape demonstrates
   the model: constructed from `RuntimeEngine`, delegates all data to capabilities, returns
   journey models, holds only journey-scoped state).
4. A lint/import gate exists proving composition services never import artifact types or
   viewer packages.
5. No M6 capability contract is altered by M7.0.

## Non-goals (M7.0)

- No concrete journey service implementation (that is M7.1+).
- No new artifacts, no compiler/publisher/loader changes.
- No application/UI code.

## Acceptance Criteria (to exit M7.0 into M7.1+)

- The six questions above have written, accepted answers (this document).
- A reference composition service proves the model compiles and is tested against faked
  capabilities.
- The import gate passes: composition services depend only on `RuntimeEngine` + domain types,
  never on `@navi/runtime` internals (artifact types, engines) or viewer libraries.
- ADR-015 compatibility baseline remains green (no M6 signature changes).

## Technical Considerations

- Mirror the M6 discipline: one concern per service, stable interfaces, deterministic where
  possible, viewer-agnostic.
- Composition services are the **last runtime layer before the application**. The application
  owns rendering, viewer state, async pacing, and persistence of journey state.
- Treat the M6 capabilities as the stable "standard library" of the runtime; composition
  services are the "programs" written against it.

## Known Pitfalls

- Don't let a composition service become a second `RuntimeEngine` (re-implementing routing or
  search). Delegate.
- Don't add async/internal I/O — keep services synchronous; let the app pace workflows.
- Don't persist journey state inside the service — that's application responsibility.
- Don't silently extend the artifact pipeline from M7 — that belongs to M6 (ADR-015).
- Don't number M7.1+ service work before M7.0 is accepted — the model must precede instances.
