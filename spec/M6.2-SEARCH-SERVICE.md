# M6.2 — Search Service

## What

Create a `SearchService` capability on `RuntimeEngine` that provides text search, autocomplete, ID lookup, and category filtering — without exposing `SearchEngine` or its internal scoring to application code.

Currently `RuntimeEngine` exposes `engine.search.query(text, config?)` via a low-level `SearchAPI` wrapper that returns raw `{ entry, score }` results. The goal is to replace `SearchAPI` with a proper domain service that returns a consistent `SearchResult` type, exposes application-oriented methods (`search`, `autocomplete`, `findById`, `findByCategory`), and treats `SearchEngine` as an internal implementation detail (just as `NavigationService` treats `RoutingEngine`).

**Public (application-facing):**

```
Application
      │
RuntimeEngine
      │
engine.search
```

**Internal (implementation):**

```
SearchService
      │
SearchEngine
      │
SearchIndex
```

### Invariants

- **SearchService never indexes data.** It only queries the immutable `SearchIndex` contained in `LoadedPackage`. The compiler builds the index; the runtime queries it.
- **SearchService is deterministic.** Given the same `SearchIndex` and query, it always returns the same ordered results. No caching, no usage history, no personalization.
- **SearchResult is readonly.** Everything crossing capability boundaries is immutable — consistent with ADR-013 and `LoadedPackage`.

## Success Criteria

1. `RuntimeEngine` exposes `engine.search` as a `SearchService` with: `search`, `autocomplete`, `findById`, `findByCategory`
2. `search()` and `autocomplete()` return `SearchResult[]` with real search scores; `findByCategory()` returns `SearchResult[]`; `findById()` returns `SearchResult | undefined`
3. `SearchResult.score` is optional (`score?: number`) — only populated when a ranking algorithm produced it
4. `SearchResult` exposes raw data fields (`buildingId?`, `floor?`) — not formatted strings, which belong to UI
5. `SearchCategory` derives from `SearchEntry["type"]` — not a separate union that drifts
6. A private `mapEntry(entry)` helper guarantees every method returns the same shape
7. `search(query)` delegates to the existing `SearchEngine` for scoring and ranking — no new search algorithm
8. `autocomplete(prefix)` delegates to `SearchEngine` for ranking — the service doesn't know *how* autocomplete works
9. `SearchAPI` class is removed; `SearchEngine` exports remain for backward compat but `SearchService` wraps it internally
10. No changes to the compiler, publisher, loader, or `LoadedPackage` format
11. All existing tests pass; new tests cover all methods and edge cases

## Non-goals

- No changes to `SearchEngine`, `SearchEntry`, or `SearchIndex` types
- No fuzzy ranking algorithms beyond what `SearchEngine` already provides
- No recent searches, search history, or persistence
- No spelling correction or "did you mean"
- No popularity scoring or usage-based ranking
- No semantic search or vector embeddings
- No filters, facets, or advanced query syntax
- No UI formatting of results (subtitle, location strings, etc.)

## Acceptance Criteria

- `engine.search.search("Library")` returns `SearchResult[]` ranked by relevance (score descending)
- `engine.search.search("")` returns `[]` (empty query)
- `engine.search.search("ZZZ_NONEXISTENT")` returns `[]` (no matches)
- `engine.search.autocomplete("Lib")` returns prefix matches ranked by the underlying SearchEngine
- `engine.search.autocomplete("")` returns `[]`
- `engine.search.autocomplete("ZZZ_NONEXISTENT")` returns `[]`
- `engine.search.findById("some-id")` returns `SearchResult` for a valid ID, `undefined` for an unknown ID
- `engine.search.findByCategory("room")` returns all room entries sorted by label
- `engine.search.findByCategory("building")` returns all building entries sorted by label
- `engine.search.findByCategory("unknown")` returns `[]`
- All methods produce results through the same `mapEntry` shape: `{ id, title, category, nodeId, score?, buildingId?, floor? }`
- `SearchResult.category` derives from `SearchEntry["type"]`
- `score` is absent (`undefined`) for `findById` and `findByCategory` results; only `search()` and `autocomplete()` populate it
- Gracefully handles `searchIndex` being `undefined` (all methods return empty/falsy)
- All existing tests pass unchanged

## API

```ts
// SearchCategory derives from the domain type — adding new entry types propagates automatically
type SearchCategory = SearchEntry['type']

// SearchResult is the runtime representation of searchable content
// It is a domain model, not a mapped SearchEntry. Compiler format ≠ runtime format.
interface SearchResult {
  readonly id: string
  readonly title: string
  readonly category: SearchCategory
  readonly nodeId: string
  readonly score?: number
  readonly buildingId?: string
  readonly floor?: number
}

class SearchService {
  constructor(pkg: LoadedPackage)

  search(query: string): SearchResult[]
  autocomplete(prefix: string): SearchResult[]
  findById(id: string): SearchResult | undefined
  findByCategory(category: SearchCategory): SearchResult[]
}
```

## Technical Considerations

- `SearchService` wraps `SearchEngine` — does not reimplement scoring or tokenization
- `SearchEngine` is constructed from `LoadedPackage.searchIndex` — must handle `undefined` gracefully (all methods return `[]` or `undefined`)
- Follows ADR-013 Capability pattern: initialized from `LoadedPackage`, single responsibility, no persistence
- `mapEntry(entry)` is a private helper that converts `SearchEntry` → `SearchResult`, guaranteeing uniform shape
- `SearchResult` is the runtime representation — distinct from the compiler's `SearchEntry` format, following the same philosophy as `NavigationArtifacts` vs `LoadedPackage`
- `score` is only present where ranking makes sense: `search()` and `autocomplete()`. `findById()` and `findByCategory()` omit it.
- `autocomplete()` delegates to `SearchEngine` — the service doesn't know how ranking works internally
- Capability lifecycle follows the same pattern as M6.1 (`NavigationService`) — construct from `LoadedPackage`, provide stable public API, no mutable state

## Known Pitfalls

- Don't delete `SearchEngine` or its exports — other tests and downstream code may import them directly
- `SearchAPI` removal must be coordinated — update all `engine.search.query()` callers to `engine.search.search()`
- The existing `PositionAPI` and `DataAPI` are not changing — avoid scope creep
- `searchIndex` may be `undefined` — every method must check before operating
- `SearchResult` name may collide with `SearchEngine.SearchResult` — use qualified imports or rename the engine's internal type
- No UI formatting leaks from runtime — `buildingId` and `floor` are exposed as raw data; presentation decisions belong to the application layer
