# M7.1a — Journey Model

## Problem

M7.0 proved that composition services can orchestrate capabilities without touching artifacts,
viewers, or the pipeline. But it left the **workflow vocabulary** undefined. The reference
service returns a flat `SuggestedJourney` — a snapshot, not a flow.

M7.1 (Visitor Journey) needs a *stateful, step-oriented journey model* that:

- Lets a service own the full workflow from "where am I" to "show me the panorama."
- Supports both automatic steps (locate, search, route, panorama lookup) and interactive steps
  (the user must choose among candidates, grant permission, confirm a reroute).
- Keeps the application as a pure renderer — it executes intents and presents interactions,
  but never owns workflow decisions.

## Goals

1. Define a **Journey** type that wraps a sequence of steps, current position, and completion
   status — a workflow container, not a data snapshot.
2. Define a **JourneyStep** discriminated union that covers every phase of a point-to-point
   journey: locate, search, navigate, arrive, panorama — plus interaction pausing.
3. Define **InteractionStep** as a first-class concept: the service says "I cannot continue
   without input," the application renders the choice, and the service proceeds.
4. Keep the model **UI-agnostic** — no viewer, map, camera, or rendering types.
5. Keep the model **pipeline-agnostic** — no `LoadedPackage`, `NavigationGraph`, artifact
   types, or compiler/publisher types.

## Non-goals

- M7.1a defines the **types only**. No `VisitorJourneyService` implementation.
- No routing algorithms, search heuristics, or capability orchestration logic.
- No UI components, views, or rendering code.
- No policy layer (role-based journeys, building closures, hours of operation).

## Principle

> **A Journey is the execution state of a composition workflow. It contains only workflow
> state and derived results. It never owns capabilities, artifacts, viewers, or platform
> resources.**

## Journey Model

```
Journey
├── id: string
├── request: string           (original query: "Library")
├── position: LatLng
├── steps: JourneyStep[]
├── currentStepId: string     (stable identity for UI tracking)
├── currentIndex: number
├── status: JourneyStatus     (not-started / in-progress / waiting-on-user / complete / failed)
└── isComplete(): boolean
    next(): JourneyStep
    previous(): JourneyStep
    current(): JourneyStep
    respond(response: unknown): void
    reset(): void
```

## Step Types

### Automatic steps (service proceeds alone)

```
JourneyStep
├── LocateStep
│   └── location: LocationContext
│
├── SearchStep
│   └── results: SearchResult[]
│
├── NavigateStep
│   ├── route: Route
│   ├── destination: BuildingResult
│   └── entrance: EntranceResult
│
├── ArrivalStep
│   ├── building: BuildingResult
│   └── floor: number
│
└── PanoramaStep
    └── panorama: PanoramaResult
```

### Interactive steps (service needs human input)

```
JourneyStep
├── SelectDestinationStep
│   ├── query: string
│   └── candidates: SearchResult[]
│
├── SelectEntranceStep
│   ├── building: BuildingResult
│   └── entrances: EntranceResult[]
│
└── ConfirmStep
    ├── prompt: string
    └── options: ConfirmOption[]
```

## Interaction Protocol

When the service encounters ambiguity, it produces an interaction step and sets status to
`waiting-on-user`. The application renders the choice, collects the user's input, and passes
it back. **The service never resolves the choice itself** — it only defines what choices exist
and what happens after one is made.

```ts
// Service produces SelectDestinationStep, sets status = 'waiting-on-user'
const step = journey.current()

if (step.kind === 'select-destination') {
    // Application: render candidates, wait for user
    const choice = await showPicker(step.candidates)
    // Application: send the result back through Journey
    journey.respond(choice.id)
    // Journey advances status to 'in-progress' and moves to next automatic step
}
```

`Journey.respond()` is defined on the **Journey**, not the step:

```ts
class Journey {
    respond(response: unknown): void
}
```

The response type is determined by the current step's kind:
- `SelectDestinationStep` → expects `string` (the chosen candidate ID)
- `SelectEntranceStep` → expects `string` (the chosen entrance ID)
- `ConfirmStep` → expects `boolean`

### Rules

- **JourneyStep is immutable.** Steps are snapshot DTOs — they have no methods, callbacks,
  or promise resolvers.
- **Interaction steps contain only data.** Candidates, labels, prompts — never UI components,
  render hints, or HTML.
- **Journey owns progression.** `next()`, `previous()`, `respond()`, and `reset()` are
  dispatched on the Journey, not distributed across steps.

## JourneyStatus

```ts
type JourneyStatus =
  | 'not-started'
  | 'in-progress'
  | 'waiting-on-user'
  | 'complete'
  | 'failed'
```

## Acceptance Criteria

1. `Journey` is a class with `next()`, `previous()`, `current()`, `respond()`, `reset()`,
   and `isComplete()`.
2. `JourneyStep` is a discriminated union — each variant has a unique `kind` field and
   an `id` string for stable UI tracking.
3. Interaction steps are pure data DTOs — no methods, callbacks, or promise resolvers.
   `Journey.respond()` handles progression.
4. No `JourneyStep` variant contains `LoadedPackage`, `NavigationGraph`, `SearchIndex`,
   `BuildingIndex`, `PanoramaIndex`, `POIIndex`, or any viewer/UI library type.
5. The model is exported from `packages/runtime/src/composition/` (same module as
   `CompositionService`).
6. A unit test proves every step kind can be constructed, discriminated, and navigated.

## Technical Considerations

- **File location:** `packages/runtime/src/composition/journey-model.ts`
- **Export:** via `src/composition/index.ts` barrel, then `src/index.ts` package barrel.
- **Dependencies:** `@navi/core` (LatLng types), M6 capability DTOs
  (LocationContext, SearchResult, BuildingResult, EntranceResult, Route, PanoramaResult).
- **No runtime dependencies on RuntimeEngine** — the model is a pure data container.
  RuntimeEngine is only needed for *services* that produce journeys.
- **Journey.respond()** is the only mutation point on the model — it validates the response
  against the current interaction step and advances state. No callbacks, no promises stored
  in DTOs.

## Known Pitfalls

- **The "god step" risk:** A step variant with 10 optional fields. Mitigate by keeping
  each variant minimal — only the fields that step *needs*.
- **Application coupling:** An interaction step that includes HTML or render hints.
  Mitigate: interaction steps contain *data* (candidates, labels, prompts), not presentation.
- **State explosion:** A journey with too many granular steps. Mitigate: keep steps at the
  natural workflow boundary (locate, search, navigate, arrive, panorama). Sub-steps
  (e.g., "calculating route") are internal to the service.
