# M6.4 — Location Service

## What

Create a `LocationService` capability on `RuntimeEngine` that answers **"Where am I?"** — snapping coordinates to the nearest node, resolving which building or floor a position belongs to, and determining indoor/outdoor context — without exposing spatial algorithms, graph internals, or position engine details to application code.

Currently `RuntimeEngine` exposes `engine.position` as a stateful `PositionAPI` that stores the last GPS position via `updateGps()` and returns it via `getCurrentPosition()`. The goal is to replace `PositionAPI` with a stateless `LocationService` that answers position-based queries deterministically — given a position, return the relevant context.

**Capability boundaries:**

| Capability | Answers |
|------------|---------|
| NavigationService | "How do I travel?" |
| SearchService | "What exists?" |
| BuildingService | "Tell me about places." |
| LocationService | "Where am I?" |

**Public (application-facing):**

```
Application
      │
RuntimeEngine
      │
engine.location
```

**Internal (implementation):**

```
LocationService
      │
Runtime spatial index
      │
LoadedPackage.nodes
```

### Invariants

- **LocationService never stores state.** Every method takes a `position` parameter and returns results deterministically. No GPS history, no cached position.
- **`resolve()` is the canonical implementation.** Every other public method is a projection of the `LocationContext` returned by `resolve()`. This guarantees the five public methods never diverge.
- **LocationService never computes routes.** Nearest-node snapping is distance-based (not path-based). Routing belongs to NavigationService.
- **LocationService never searches.** Building/floor lookup uses spatial proximity, not the search index.
- **LocationService never modifies package data.** It's a read-only consumer of `LoadedPackage`.
- **LocationService is deterministic.** Given the same `LoadedPackage` and position, it always returns the same results.

## Success Criteria

1. `RuntimeEngine` exposes `engine.location` as a `LocationService` with: `resolve(position)` as the only primitive, plus convenience projections `snapToNode`, `getBuilding`, `getFloor`, `isInsideBuilding`
2. `resolve(position)` returns a `LocationContext` — computed once by a private `resolveContext()`, shared by all public methods
3. `snapToNode(position)` returns `SnapResult | undefined` — containing the nearest `NavNode` and distance, stateless
4. `getBuilding(position)` returns `BuildingResult | undefined` — projection of `resolve().building`
5. `getFloor(position)` returns `number | undefined` — projection of `resolve().node.node.floor`
6. `isInsideBuilding(position)` returns `boolean` — whether the resolved location belongs to an indoor navigation space
7. `SnapResult` exposes `node: NavNode` (the runtime navigation node) — no duplicated DTO
8. `LocationContext` does not duplicate `floor` — it's accessible through `node.node.floor`
9. `PositionAPI` class is removed from `RuntimeEngine`; `PositionEngine` and `GpsResolver` remain importable
10. No changes to the compiler, publisher, loader, or `LoadedPackage` format
11. All existing tests pass; new tests cover all methods and edge cases

## Non-goals

- No GPS receiver or browser geolocation integration — that belongs in application code
- No route computation — that's NavigationService
- No position history or tracking — LocationService is stateless
- No indoor positioning algorithms (WiFi, BLE, QR) — those are future capabilities
- No changes to graph types, building types, or `LoadedPackage`
- No panorama lookup — that's PanoramaService

## Acceptance Criteria

- `engine.location.snapToNode({lat, lng})` returns `SnapResult` with `NavNode` and distance for a coordinate near a node, `undefined` for empty graph
- `engine.location.snapToNode()` is stateless — same input always returns same result
- `engine.location.getBuilding({lat, lng})` returns `BuildingResult` for a position within a building, `undefined` for open space
- `engine.location.getFloor({lat, lng})` returns `number` for a position near a node with known floor, `undefined` otherwise
- `engine.location.isInsideBuilding({lat, lng})` returns boolean based on published building geometry
- `engine.location.resolve({lat, lng})` returns `LocationContext` with all available fields
- `resolve()` is the canonical implementation — convenience methods are projections, and any two calls with the same input produce identical results
- All methods gracefully handle empty graph or missing buildingIndex
- `PositionAPI` no longer exists on `RuntimeEngine`

## API

```ts
interface SnapResult {
  readonly node: NavNode
  readonly distance: number
}

interface LocationContext {
  readonly position: LatLng
  readonly node?: SnapResult
  readonly building?: BuildingResult
  readonly isIndoor: boolean
}

class LocationService {
  constructor(pkg: LoadedPackage)

  resolve(position: LatLng): LocationContext

  // Convenience projections — all delegate to resolve()
  snapToNode(position: LatLng, floor?: number): SnapResult | undefined
  getBuilding(position: LatLng): BuildingResult | undefined
  getFloor(position: LatLng): number | undefined
  isInsideBuilding(position: LatLng): boolean
}
```

## Technical Considerations

- `resolve()` is the canonical implementation — a private `resolveContext()` computes all location data in a single pass. Every public method (including `resolve()`) calls `resolveContext()`, so `getBuilding()` and `getFloor()` never independently repeat the O(n) node scan.
- `SnapResult` returns `node: NavNode` — the runtime's navigation node type. This is the single source of truth; no DTO duplicates its fields. Consumers access `node.node.floor`, `node.node.buildingId`, etc.
- `LocationContext` deliberately excludes `floor` — it's available at `context.node.node.floor`. Removing duplication gives one source of truth.
- `isInsideBuilding` reports whether the resolved location belongs to an indoor navigation space, determined from published building geometry.
- `getFloor()` is implemented as `resolve(position).node?.node.floor` — a thin projection over `resolve()`.
- Follows ADR-013 Capability pattern: initialized from `LoadedPackage`, single responsibility, no persistence.
- Replaces `PositionAPI` on `RuntimeEngine` — but `PositionEngine` and `GpsResolver` remain exportable for backward compatibility.

## Known Pitfalls

- Don't make `LocationService` stateful — resist adding `updateGps()` or `currentPosition` fields
- `getFloor()` depends on graph nodes having floor data — returns `undefined` if no nearby node
- `isInsideBuilding()` uses published building geometry — precision depends on what the compiler publishes
- `PositionAPI` removal must be coordinated with any code calling `engine.position.*` — update to `engine.location.*`
- `PositionEngine` and `GpsResolver` remain available for direct import if applications need the old stateful pattern
- Don't add route-aware snapping (walking distance vs straight-line) — that's a NavigationService concern
