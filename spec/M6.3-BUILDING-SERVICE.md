# M6.3 — Building Service

## What

Create a `BuildingService` capability on `RuntimeEngine` that provides building lookup, nearest-building search, entrance metadata, and point-in-building detection — without exposing `BuildingIndex` or `BuildingEntry` internals to application code.

Currently building data is accessible only through `DataAPI.getBuildings()` and `DataAPI.getBuilding(id)`, which return raw `BuildingEntry` objects from the compiler format. The goal is to create a proper domain service that returns a consistent `BuildingResult` type, exposes application-oriented methods (`get`, `list`, `findNearest`, `getEntrances`, `findContaining`), and follows the same capability pattern established by `NavigationService` and `SearchService`.

**Public (application-facing):**

```
Application
      │
RuntimeEngine
      │
engine.buildings
```

**Internal (implementation):**

```
BuildingService
      │
BuildingIndex (LoadedPackage)
```

### Invariants

- **BuildingService never performs graph traversal.** It may return entrance IDs, but it never computes routes. NavigationService owns all route computation.
- **BuildingService never indexes data.** It only queries the immutable `BuildingIndex` contained in `LoadedPackage`.
- **BuildingService never modifies building metadata.** The runtime is a read-only consumer of the compiled index.
- **BuildingService is deterministic.** Given the same `BuildingIndex` and inputs, it always returns the same results.

## Success Criteria

1. `RuntimeEngine` exposes `engine.buildings` as a `BuildingService` with: `get`, `list`, `findNearest`, `getEntrances`, `findContaining`
2. `get(id)` returns a single `BuildingResult` or `undefined`
3. `list()` returns all buildings sorted by name
4. `findNearest(position)` returns the nearest building by Euclidean distance from `BuildingEntry.position`
5. `getEntrances(id)` returns `EntranceResult[]` in deterministic order (sorted by name) — never exposes raw entrance objects
6. `findContaining(position)` returns `BuildingResult | undefined` — determines whether the position lies within a building using the published building geometry
7. `BuildingResult` is a readonly domain type exposing only application-relevant fields — no compiler internals like `nodeId`
8. `EntranceResult` is a readonly domain type with `{ id, name, nodeId, position }`
9. No changes to the compiler, publisher, loader, or `LoadedPackage` format — consumes `LoadedPackage.buildingIndex` only
10. All existing tests pass; new tests cover all methods and edge cases

## Non-goals

- No route computation (`routeToBuilding`, `navigateToEntrance`) — those are NavigationService concerns
- No accessibility-aware entrance filtering (future capability)
- No panorama lookup on buildings (PanoramaService concern)
- No indoor positioning (LocationService concern)
- No changes to `BuildingEntry`, `BuildingIndex`, or `FloorEntry` types
- No changes to `DataAPI` — it remains separately available for low-level access

## Acceptance Criteria

- `engine.buildings.get("b1")` returns `BuildingResult` for a valid ID, `undefined` for unknown ID
- `engine.buildings.list()` returns all buildings sorted by name
- `engine.buildings.findNearest({lat, lng})` returns the closest `BuildingResult` by position
- `engine.buildings.findNearest()` on empty index returns `undefined`
- `engine.buildings.getEntrances("b1")` returns `EntranceResult[]` sorted by name for a valid building
- `engine.buildings.getEntrances("unknown")` returns `[]`
- `engine.buildings.findContaining({lat, lng})` returns the building containing that point, or `undefined`
- All methods gracefully handle `buildingIndex` being `undefined`
- All results are readonly (compile-time check through TypeScript `readonly`)
- All existing tests pass unchanged

## API

```ts
interface BuildingResult {
  readonly id: string
  readonly name: string
  readonly code: string
  readonly category: string
  readonly position: LatLng
  readonly entrances: readonly string[]   // entrance IDs only
  readonly floors: readonly string[]      // floor labels
}

interface EntranceResult {
  readonly id: string
  readonly name: string
  readonly position: LatLng
}

class BuildingService {
  constructor(pkg: LoadedPackage)

  get(id: string): BuildingResult | undefined
  list(): BuildingResult[]
  findNearest(position: LatLng): BuildingResult | undefined
  getEntrances(buildingId: string): EntranceResult[]
  findContaining(position: LatLng): BuildingResult | undefined
}
```

## Technical Considerations

- `BuildingService` extracts `buildingIndex` from `LoadedPackage` — handles `undefined` gracefully
- `BuildingResult` is the runtime representation of a building — distinct from the compiler's `BuildingEntry` format. Compiler internals like `nodeId` are not exposed
- `findContaining(position)` uses the published building geometry (bounds, footprint, or centroid-based approximation) to determine containment — O(n) over buildings, fine for campus-scale
- `findNearest(position)` uses Euclidean distance from `BuildingEntry.position` — O(n), fine for campus-scale (under 500 buildings)
- Follows ADR-013 Capability pattern: initialized from `LoadedPackage`, single responsibility, no persistence
- `getEntrances(buildingId)` returns `EntranceResult[]` sorted by name — deterministic ordering
- `list()` returns buildings sorted by name for deterministic ordering
- `BuildingResult.entrances` exposes only entrance IDs — applications call `getEntrances(id)` for full details, avoiding data duplication

## Known Pitfalls

- Don't leak `BuildingEntry` or compiler types through the public API — `BuildingResult` is the domain type
- `buildingIndex` may be `undefined` — every method must check before operating
- `findContaining()` depends on published building geometry — if geometry is unavailable or centroid-only, containment checks may be approximate; document this limitation
- Nearest-building uses Euclidean distance, not walkable distance — that's a LocationService concern
- Don't add `routeToBuilding()` or `navigateToEntrance()` — those blur the boundary between BuildingService and NavigationService
- `nodeId` is intentionally excluded from `BuildingResult` — it's a compiler implementation detail; applications should reference buildings by `id` only
