# M7.0 — Composition Layer Execution Plan

## Nature of this milestone

M7.0 is **architectural**, not feature. It establishes the composition model (SPEC M7.0) and a
reference service that proves the model, **before** any concrete journey service (M7.1+) is
built. This keeps M7 as disciplined as M6: define the layer, then populate it.

Per ADR-015, M7 may add composition services but must not reshape the frozen M6 capability
surface. M7.0's job is to make "what a composition service is" unambiguous and enforceable.

## Tasks

### T1. Define the CompositionService contract

Create `packages/runtime/src/composition/composition-service.ts` with:
- A `CompositionService` marker interface (tagging type; all M7 services implement it).
- Shared journey-model primitives if needed (e.g. `JourneyStep`, `Itinerary`) — but keep them
  minimal; concrete shapes belong to M7.1+ services.
- A doc comment stating the invariant: constructed from `RuntimeEngine`, delegates all data to
  capabilities, viewer-agnostic, no artifact imports.

**Files to create:** `packages/runtime/src/composition/composition-service.ts`

**Acceptance:** `CompositionService` is exported; its contract text matches SPEC M7.0 invariants.

---

### T2. Reference composition service (template)

Create one minimal, **deliberately generic and instructional** reference service in
`packages/runtime/src/composition/` that demonstrates the model end-to-end: constructed from
`RuntimeEngine`, composes ≥2 capabilities into a small journey result, holds only
journey-scoped state (e.g. a current-step index), synchronous. This is the template M7.1+
services copy. Name it to make its non-production nature obvious — `ReferenceCompositionService`
(preferred), `CompositionTemplateService`, or `ExampleCompositionService`. Keep it trivial
(e.g. it composes `location.resolve` + `search.search` + `panoramas.findNearest` into a
"suggested starting point" workflow) purely to prove the shape. It exists to *prove the
architecture*, not to ship a feature — future developers must never mistake it for product code.

**Files to create:** `packages/runtime/src/composition/reference-composition-service.ts`

**Acceptance:** Reference service constructed from `RuntimeEngine`; delegates every data
question to a capability; returns a journey-shaped result; no artifact-type imports; no viewer
imports; name signals "template, not feature".

---

### T3. Composition contract test + import gate

Write `composition-contract.test.ts`:
- Construct reference service over a faked `RuntimeEngine` (capability interfaces only) — proves
  services are testable without loading a package.
- Assert journey output and step transitions.
- Assert the service never reads artifacts (it only calls capability methods).

Add a layer-boundary gate (`scripts/check-layer-boundaries.mjs`) that fails if any file under
`src/composition/` imports forbidden modules (artifact types, `LoadedPackage`, `graph/*`,
`loader/*`, `compiler/*`, `publisher/*`, viewer packages). The script is named generically
because it is intended to grow into a full architectural linter (later it can also verify
`runtime → loader only`, `loader → publisher only`, `publisher → compiler only`). Wire it so
it runs in CI.

**Files to create:** `packages/runtime/src/composition/__tests__/composition-contract.test.ts`,
`scripts/check-layer-boundaries.mjs`

**Acceptance:** Contract test passes; gate passes; gate is runnable (`node scripts/check-layer-boundaries.mjs`).
