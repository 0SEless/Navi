# M7.2 — Routing Preferences Plan

Based on `spec/M7.2-ROUTING-PREFERENCES.md`. Validates that composition services express
intent while capabilities determine behavior — proving ADR-013/014/015 with a single
service and a preference parameter, without duplicating workflow.

## Architecture Invariants (from spec)

- Separate composition services exist when the *workflow* changes, not the preference
- `VisitorJourneyService` is the only point-to-point composition service — future workflow
  types (CampusTour, Emergency) will be separate services
- Accessibility is a routing policy communicated via `RoutePreferences`, never computed in
  the composition layer
- No new step types — accessibility is not a workflow
- No graph/package/artifact/compiler/loader/viewer access
- The only visible difference between `mode: 'standard'` and `mode: 'accessible'` is the
  `NavigateStep.route` value
- `RoutePreferences.mode` defaults to `'standard'` for backward compatibility
- `JourneyRequest` replaces positional `(position, destination)` on `begin()`

## Tasks

### T1 — JourneyRequest and RoutePreferences types

**Files to touch:**
- `packages/core/src/types.ts` or a new `packages/core/src/journey.ts`
- `packages/core/src/index.ts` (extend exports)

**What:**
Define the shared types that communicate routing intent from composition to capability:

```ts
export type RouteMode = 'standard' | 'accessible'

export interface RoutePreferences {
  mode?: RouteMode
}
```

**Key decisions:**
- Types live in `@navi/core` because they are shared contracts between composition and
  capabilities
- `mode` is optional — defaults to `'standard'` when absent (backward compatible)
- `JourneyRequest` uses `origin` (not `position`) for clarity — the request describes
  a journey from A to B
- Do NOT define future modes (`indoor`, `scenic`, `fastest`). Only the two that exist today.
- Do NOT extend `JourneyRequest` beyond `{ origin, destination, routing }`. Future fields
  (`language`, `timeConstraints`, `visitorRole`) belong in later milestones.
- Export from `packages/core/src/index.ts` so available to runtime and downstream
- `JourneyRequest` is NOT in core — it lives in `packages/runtime/src/composition/` as a
  workflow input, not a domain contract

**Edge cases:**
- `mode: undefined` → treated as `'standard'`
- `mode: 'accessible'` with a capability that doesn't support it → capability handles
  gracefully (falls back or returns null — service handles null via `markFailed`)
- `routing: undefined` → no preferences, treated as standard
- `routing: {}` → no mode, treated as standard
- No validation needed at the type level — `RouteMode` is a union, TypeScript enforces it

**Acceptance:**
- `RouteMode` and `RoutePreferences` compile and are publicly exported from `@navi/core`
- `JourneyRequest` is defined in `packages/runtime/src/composition/` (not in core)
- No existing tests break

### T2 — Navigation capability accepts RoutePreferences

**Files to touch:**
- `packages/runtime/src/engine/navigation-service.ts` (extend `findRoute` signature)
- `packages/runtime/src/engine/index.ts` (verify exports unaffected)

**What:**
Extend `NavigationService.findRoute()` to accept optional `RoutePreferences`:

```ts
findRoute(
  fromId: string,
  toId: string,
  preferences?: RoutePreferences,
): Route | null {
  const _mode = preferences?.mode ?? 'standard'
  // existing routing logic unchanged
  return this.engine.findRoute(fromId, toId)
}
```

The parameter is additive and optional — no existing callers break. `VisitorJourneyService`
will be updated in T4 to pass preferences through.

**Key decisions:**
- Standard `NavigationService` accepts but ignores the mode for now. Behavior is identical
  regardless of what mode is passed. This is correct — the standard service doesn't know
  about accessibility.
- A future `AccessibleNavigationService` (or a test fake) interprets the mode differently.
- Import `RoutePreferences` from `@navi/core`.

**Acceptance:**
- `findRoute(a, b)` without preferences returns existing behavior
- `findRoute(a, b, { mode: 'standard' })` returns same result
- `findRoute(a, b, { mode: 'accessible' })` compiles and runs (same result on standard svc)
- Existing engine tests pass

### T3 — Fake accessible navigation service (test helper)

**Files to touch:**
- `packages/runtime/src/composition/__tests__/visitor-journey-service.test.ts` (extend)

**What:**
Add a test-only fake that implements the same `NavigationService` contract but returns a
different route when `mode === 'accessible'`:

```ts
class FakeAccessibleNavigationService {
  findRoute(fromId: string, toId: string, preferences?: RoutePreferences): Route | null {
    if (preferences?.mode === 'accessible') {
      return {
        path: [{ lat: 14.1, lng: 121.1 }],
        instructions: ['Take accessible path'],
        totalDistance: 350,
        totalDuration: 180,
        fromLabel: 'Start',
        toLabel: 'Library Accessible',
        travelTime: { seconds: 180, minutes: 3, formatted: '3 min' },
      }
    }
    // fallback to standard route
    return fakeRoute()
  }
}
```

The fake's `findRoute` checks `preferences?.mode === 'accessible'` and returns a distinct
route when true. This simulates what a real accessible navigation service would do with
actual accessibility graph data — without requiring that data for the test.

**Key decisions:**
- No real accessibility routing logic. The milestone tests the *composition workflow*, not
  the routing engine's accessibility features.
- The fake lives in the test file, not in production code.
- A fake engine builder function creates either a standard or accessible engine:

```ts
function createEngine(
  searchResults: SearchResult[],
  panoramaResult?: PanoramaResult,
  accessible?: boolean,
) {
  return {
    navigation: accessible
      ? new FakeAccessibleNavigationService()
      : new FakeNavigationService(),
    // other capabilities unchanged
  }
}
```

**Acceptance:**
- `FakeAccessibleNavigationService` satisfies the same call signature as `NavigationService`
- It returns a observably different route when `mode === 'accessible'` than when standard

### T4 — Update VisitorJourneyService

**Files to touch:**
- `packages/runtime/src/composition/visitor-journey-service.ts` (modify)

**What:**
Update `begin()` to accept `JourneyRequest` and pass `routing` preferences through to
`findRoute`:

```ts
class VisitorJourneyService implements CompositionService {
  constructor(private readonly engine: RuntimeEngine) {}

  // New signature
  begin(request: JourneyRequest): Journey {
    const location = this.engine.location.resolve(request.origin)
    // ... rest using request.destination, request.routing
  }

  // Transitional overload preserving backward compatibility
  begin(position: LatLng, destination: string): Journey {
    return this.begin({ origin: position, destination })
  }

  advance(journey: Journey): Journey {
    // ... existing transition table, except:
    // _buildNavigateStep and _buildNavigateStepFromIds now accept
    // and pass through routing preferences:
    this.engine.navigation.findRoute(fromId, toId, journey.request.routing)
  }
}
```

**Key decisions:**
- `JourneyRequest` is defined in `packages/runtime/src/composition/journey-model.ts` (or a
  new `journey-request.ts` beside it) — not in `@navi/core`. It is a workflow input, not a
  domain contract.
- Store `request` on the Journey instance (as `journey.request`) so `advance()` can read
  `routing` preferences without needing them passed as a separate parameter.
  This requires adding `request` to the `Journey` constructor.
- Transitional overload `begin(position, destination)` prevents breaking existing callers
  (M7.0 contract test, M7.1b tests). Document as deprecated.
- `request.routing` defaults to `undefined` → `findRoute` treats as standard.
- The Journey class needs a new `request` property holding the original `JourneyRequest`.
  This is semantically correct — the request is part of the journey's execution context.

**Changes to Journey class:**
```ts
class Journey {
  readonly request: JourneyRequest

  constructor(
    id: string,
    request: JourneyRequest,
    steps: JourneyStep[],
    context?: JourneyContext,
  ) {
    this.request = request
    // ...
  }
}
```

**Edge cases:**
- `request.routing` is undefined → standard route (backward compatible)
- `request.routing.mode` is undefined → standard route
- `request.routing.mode` is `'accessible'` but engine doesn't support it → engine returns
  standard route (same failure path as `findRoute` returning null)
- Old `begin(position, destination)` overload → wraps in `JourneyRequest` with no routing

**Acceptance:**
- All existing M7.1b tests pass without changes (old overload preserves behavior)
- New `begin(request)` signature produces identical results when `routing` is not set
- `begin(request)` with `{ routing: { mode: 'accessible' } }` produces a NavigateStep
  with different route when engine supports it
- Layer-boundary gate passes

```ts
const standardEngine = createEngine(fakeSearchSingle(), fakePanorama(), false)
const accessibleEngine = createEngine(fakeSearchSingle(), fakePanorama(), true)

const standardJourney = standardEngine.begin({ origin: POS, destination: 'Library' })
const accessibleJourney = accessibleEngine.begin({ origin: POS, destination: 'Library', routing: { mode: 'accessible' } })

standardEngine.advance(standardJourney); standardJourney.next()
accessibleEngine.advance(accessibleJourney); accessibleJourney.next()

// Both produce NavigateStep
expect(standardJourney.current().kind).toBe('navigate')
expect(accessibleJourney.current().kind).toBe('navigate')

// But the routes are different

// Complete both workflows and verify step counts match
standardEngine.advance(standardJourney); standardJourney.next()
accessibleEngine.advance(accessibleJourney); accessibleJourney.next()
standardEngine.advance(standardJourney); standardJourney.next()
accessibleEngine.advance(accessibleJourney); accessibleJourney.next()
standardEngine.advance(standardJourney)
accessibleEngine.advance(accessibleJourney)

expect(standardJourney.isComplete()).toBe(true)
expect(accessibleJourney.isComplete()).toBe(true)
expect(standardJourney.steps.length).toBe(accessibleJourney.steps.length)
```
