# M6.5b — Panorama Service

## What

Create a `PanoramaService` capability on `RuntimeEngine` that answers **"What does this place look like?"** — exposing panorama metadata and hotspot relationships as immutable domain DTOs, without owning or knowing anything about rendering, camera orientation, viewer transitions, or any specific 360° viewer library (Pannellum, Marzipano, etc.).

M6.5a already extended the pipeline (compiler → publisher → loader) so that panorama data ships as the optional `panoramaIndex` artifact inside `LoadedPackage`. M6.5b is the runtime capability that consumes that artifact and answers domain questions about it. The layer stack is now fully aligned:

```
Compiler
    ↓
PanoramaIndex
    ↓
Publisher
    ↓
Package
    ↓
Loader
    ↓
LoadedPackage
    ↓
PanoramaService
    ↓
Application Viewer (Pannellum)
```

**Capability boundaries:**

| Capability      | Answers                  |
| --------------- | ------------------------ |
| Navigation      | How do I get there?      |
| Search          | What exists?             |
| Buildings       | Tell me about this place.|
| Location        | Where am I?              |
| Panorama        | What does this look like?|

**Public (application-facing):**

```
Application
      │
RuntimeEngine
      │
engine.panoramas
```

**Internal (implementation):**

```
PanoramaService
      │
panoramaIndex artifact (LoadedPackage)
```

### Invariants

- **PanoramaService is viewer-agnostic.** It exposes panorama metadata and hotspot relationships only. Rendering, camera orientation, transitions, hotspot interaction, and viewer state belong to the application layer.
- **PanoramaService never imports, references, or depends on any viewer library** (Pannellum, Marzipano, HTML, CSS, DOM, React, camera math). Its return types contain only domain primitives: ids, `LatLng`, yaw/pitch, target ids.
- **PanoramaService never modifies package data.** It is a read-only projection of `LoadedPackage.panoramaIndex`.
- **PanoramaService is deterministic.** Given the same `LoadedPackage`, the same query always returns the same result.
- **Hotspot targets stay as data.** A hotspot carries a `target` (an id or URL) and a normalized `type` (`navigation` | `information` | `link`). The service projects a navigation hotspot's target into `targetPanoramaId` (when the target matches a known panorama id) or `targetRoomId` (otherwise) — derived purely from published data, no artifact change.
- **Returns immutable DTOs.** All returned objects are `readonly` projections. No runtime types (nodes, graph) leak through.

## Success Criteria

1. `RuntimeEngine` exposes `engine.panoramas` as a `PanoramaService`.
2. `PanoramaService` exposes exactly: `get(id)`, `list(buildingId?)`, `findNearest(position)`, `getHotspots(panoramaId)`, `resolve(roomId)`.
3. `get(id)` returns a `PanoramaResult | undefined`.
4. `list(buildingId?)` returns `PanoramaResult[]`, optionally filtered by building.
5. `findNearest(position)` returns the `PanoramaResult` closest to a `LatLng`, `undefined` when no panoramas exist.
6. `getHotspots(panoramaId)` returns `HotspotResult[]` for a panorama, `[]` when not found or none.
7. `resolve(roomId)` returns the `PanoramaResult` of a panorama that contains a `navigation` hotspot targeting `roomId`, `undefined` otherwise.
8. `PanoramaResult` and `HotspotResult` are domain DTOs — no viewer concepts.
9. Gracefully handles a package with no `panoramaIndex` (returns `undefined` / `[]`).
10. No changes to the compiler, publisher, loader, `LoadedPackage` format, or any frozen artifact (M6.5a stays frozen).
11. All existing tests pass; new tests cover every method and edge case.

## Non-goals

- No Pannellum / Marzipano / 360° viewer integration — application layer only.
- No camera math, projection, or transition logic.
- No DOM, React, or rendering of hotspots.
- No changes to the `panoramaIndex` artifact schema (it is frozen by M6.5a).
- No new routing between panoramas — relationship data is published, the application decides what clicking a hotspot means.

## Acceptance Criteria

- `engine.panoramas.get(id)` returns a `PanoramaResult` with `id`, `imageAssetId`, `position`, and optional `buildingId`/`floor`/`heading`/`roomId`; `undefined` for unknown id.
- `engine.panoramas.list()` returns all panoramas; `list(buildingId)` returns only that building's panoramas; empty `[]` when none.
- `engine.panoramas.findNearest({lat,lng})` returns the closest panorama by straight-line distance; `undefined` for empty index.
- `engine.panoramas.getHotspots(panoramaId)` returns `HotspotResult[]` with `id`, `type`, `position` (yaw/pitch), and resolved `targetPanoramaId`/`targetRoomId`; `[]` for unknown panorama.
- `engine.panoramas.resolve(roomId)` returns the panorama that can navigate to that room; `undefined` when none.
- All methods tolerate a package with no `panoramaIndex`.
- No import of any viewer package anywhere in `panorama-service.ts` or its types.

## API

```ts
interface PanoramaPosition {
  readonly yaw: number    // degrees, 0-360
  readonly pitch: number  // degrees, -90 to 90
}

interface PanoramaResult {
  readonly id: string
  readonly roomId?: string
  readonly buildingId?: string
  readonly floor?: number
  readonly imageAssetId: string
  readonly heading?: number
  readonly position: LatLng
}

interface HotspotResult {
  readonly id: string
  readonly type: 'navigation' | 'information' | 'link'
  readonly position: PanoramaPosition
  readonly targetPanoramaId?: string
  readonly targetRoomId?: string
  readonly targetUrl?: string
  readonly label?: string
}

class PanoramaService {
  constructor(pkg: LoadedPackage)

  get(id: string): PanoramaResult | undefined
  list(buildingId?: string): PanoramaResult[]
  findNearest(position: LatLng): PanoramaResult | undefined
  getHotspots(panoramaId: string): HotspotResult[]
  resolve(roomId: string): PanoramaResult | undefined
}
```

## Technical Considerations

- `PanoramaService` is constructed from `LoadedPackage`; it reads `pkg.panoramaIndex?.panoramas` once and projects on demand. Mirrors `BuildingService`/`SearchService` conventions (DTOs defined alongside the service, not in `@navi/core`).
- `roomId` is intentionally optional on `PanoramaResult`. The published artifact does not carry a room id per panorama (M6.5a frozen). `resolve(roomId)` is the supported path to go from a room to its panorama: it scans for a panorama containing a `navigation` hotspot whose `target === roomId`. When such a panorama is found, its `PanoramaResult.roomId` is set to that `roomId` (so the result self-documents the resolved relationship).
- `getHotspots` derives `targetPanoramaId` vs `targetRoomId` vs `targetUrl`: for a `navigation` hotspot, if `target` matches a known panorama id it becomes `targetPanoramaId`, otherwise `targetRoomId`; for `link` it becomes `targetUrl`; `information` carries no target resolution.
- `findNearest` uses the same straight-line `distanceMeters` helper convention used by `BuildingService`.
- Follows ADR-013 Capability pattern: initialized from `LoadedPackage`, single responsibility, no persistence.

## Known Pitfalls

- Do NOT import any viewer library — that breaks the core invariant and would leak rendering concerns into the runtime.
- Do NOT expand the `panoramaIndex` artifact — M6.5a is frozen; derive everything from published data.
- `resolve(roomId)` is best-effort: a panorama is "of" a room only if it publishes a navigation hotspot to it. Don't invent a room→panorama mapping that isn't in the data.
- `findNearest` is straight-line, not route-based — routing between panoramas is an application concern.
- Graceful absence: every method must handle `panoramaIndex === undefined` (no panoramas published).
